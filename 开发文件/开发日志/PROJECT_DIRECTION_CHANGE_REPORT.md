# 项目方向变更与开发目标报告

更新时间：2026-07-09

## 一、这次变更的核心结论

当前研发拆分为两个项目方向，但定位不同：

1. `Multi-Agent Workspace` 继续推进，并作为主要发布项目。
2. 第二个项目转为 `GitHub 仓库分析 Agent 原型`，优先作为技术深度展示项目，不以当前阶段正式发布为目标。

这样调整的原因是：

- `Multi-Agent Workspace` 已有较高完成度，适合继续打磨成一个真正可发布的产品。
- 仓库分析类 Agent 更适合承载 RAG、工具调用、工作流、代码理解等 Agent 核心技术能力。
- 两个项目分工后，能够分别体现“工程落地能力”和“Agent 技术深度”，避免把所有目标硬塞进一个产品里导致失焦。

---

## 二、项目一：Multi-Agent Workspace 的新开发目标

### 2.1 新定位

`Multi-Agent Workspace` 不再强调“让很多 Agent 一起聊天”，而是收束为：

**一个面向双 Agent 协作的 AI 工作空间产品。**

它的主要目标不是展示复杂 Agent 技术栈，而是证明：

- 我能够完成一个真实可运行、可部署、可演示的 AI 产品；
- 我能够处理前后端协作、流式响应、状态管理、错误隔离、模型路由、成本展示等实际工程问题；
- 我能够把“Agent 协作”收束成普通用户可理解、可操作的产品体验，而不是概念 Demo。

### 2.2 主场景收束

项目主路径固定为两条模板化协作线路：

1. `双 Agent 报告协作`
   - 典型角色：`Writer + Reviewer`
   - 适合生成项目报告、方案说明、总结文稿

2. `双 Agent 问题分析`
   - 典型角色：`Analyst + Challenger`
   - 适合分析问题、拆解观点、正反对照

用户仍然可以修改 Agent 的具体角色设定，但产品默认引导用户优先使用双 Agent 协作，不再鼓励一个空间里同时启用太多 Agent。

### 2.3 新版本目标

下一阶段目标不是扩能力广度，而是补齐产品闭环，使其更像一个真正可发布的软件。

#### 核心目标

- 将当前多 Agent 聊天空间收束为 `双 Agent` 协作体验
- 增加模板化入口，降低用户理解成本
- 增加结构化结果区，而不是只保留消息流
- 完善运行状态反馈、错误处理、空状态、文案与交互
- 形成可部署、可录制演示视频、可用于面试展示的正式版本

#### 本项目重点体现的能力

- Web 产品化能力
- 前后端联动能力
- SSE 流式事件处理
- Agent 配置与角色编排
- 成本展示与预算控制
- 运行状态管理与错误隔离
- 产品收束和体验设计能力

#### 本项目不强行承担的能力

以下能力不作为本项目当前阶段的主打目标：

- 重型 RAG
- 复杂工具调用系统
- 面向代码仓库的深度分析
- 大规模多轮辩论
- 通用型多 Agent 平台抽象

这些能力交由第二个项目承载，避免 Workspace 项目失焦。

### 2.4 推荐的近期开发顺序

1. 收窄为双 Agent 主路径
2. 增加两套模板入口
3. 增加最终结果区
4. 完善运行过程可视化
5. 清理界面文案与空状态
6. 补 README、说明文档、演示截图或视频
7. 完成部署并形成可展示链接

### 2.5 面试叙事建议

介绍这个项目时，建议使用以下表述：

> 我做的是一个面向双角色协作的 AI 工作空间产品。它聚焦报告协作和问题分析两个高频场景，重点解决流式交互、状态管理、模型路由、成本展示和可发布产品体验，而不是单纯堆叠多个模型聊天。

## 三、项目二：GitHub 仓库分析 Agent 原型的新开发目标

### 3.1 新定位

第二个项目不以当前阶段正式发布为目标，而是作为：

**一个面向 GitHub 仓库理解的 Agent 工作流原型。**

它主要承担以下展示目标：

- RAG / 检索增强
- 工具调用
- 代码切块与仓库理解
- 多 Agent 工作流
- 结构化报告生成
- Agent 在真实复杂任务中的上下文管理能力

### 3.2 当前阶段的合理边界

该项目建议只做技术原型，不追求完整产品化。当前阶段以“可跑通、可验证、可截图、可讲述”为主。

建议边界如下：

- 先只支持公开 GitHub 仓库
- 先只聚焦 Python 仓库
- 先只做 2 个分析 Agent + 1 个 Summary Agent
- 先输出结构化分析报告
- 不做复杂账户体系、多项目管理和线上发布

### 3.3 这个项目在整体简历中的作用

这个项目不承担“产品完成度”的证明任务，而承担“Agent 技术深度”的证明任务。

推荐叙事：

> 我除了做一个完整可部署的 AI 协作产品之外，还做了一个面向 GitHub 仓库分析的 Agent 工作流原型，用来验证 RAG、工具调用、代码理解和多角色汇总在真实任务中的效果。

## 五、两个项目的新分工总结

### 项目一：Multi-Agent Workspace

- 目标：做成可发布产品
- 重点：产品化、交互、工程闭环、部署
- 形式：双 Agent 协作工作空间
- 用途：证明我能做真实 AI 产品，而不是 Demo

### 项目二：GitHub 仓库分析 Agent 原型

- 目标：做成技术深度原型
- 重点：RAG、工具调用、工作流、代码理解
- 形式：仓库分析 Agent 工作流
- 用途：证明我不只是会调模型 API，还会做复杂 Agent 任务系统

---

## 六、最终执行建议

接下来建议的行动顺序是：

1. 先继续完成 `Multi-Agent Workspace`，把它打磨成一个真正可发布、可展示的产品。
2. 将第二个项目作为技术原型推进，优先跑通核心闭环，不必急于发布。
3. 两个项目不再争夺同一个目标，而是分别承担：
   - 一个证明工程落地能力
   - 一个证明 Agent 技术深度
4. 所有后续开发都以“是否有助于这个项目承担自己的目标”作为取舍标准，避免范围蔓延。

这次调整之后，整体项目叙事会更清晰，也更适合面试与作品集展示。
