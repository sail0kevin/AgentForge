## 1. 阶段目标

先让现有轻量检索在结构、召回和用户链路上正确，再依据评测决定是否引入 embedding 或 pgvector。

## 2. P1-6：Markdown 结构切块

修改前：Markdown 在 `parseFile` 中先删除标题标记，随后 `chunkMarkdown` 无法识别章节。

计划：

- [ ] 原始 Markdown 用于结构分析；
- [ ] 每个 chunk 单独生成清洗文本；
- [ ] 保存标题层级、文档 ID、准确行号和 chunk 索引；
- [ ] 增加多级标题、代码块和长章节测试。

验收：两个标题至少生成两个可区分章节，来源和行号可以回到原文。

## 3. P1-7：TF-IDF 零召回

修改前：查询词存在于全部 chunk 时 IDF 为 0，所有结果被过滤；tokenizer 去重后无法计算真实词频。

计划：

- [ ] 修改 IDF 平滑；
- [ ] 文档 token 保留频次；
- [ ] 查询 token 与文档频次分离；
- [ ] 预计算单次查询中的 chunk token，避免重复分词；
- [ ] 明确同分排序规则和最低分阈值。

验收数据：

- [ ] 查询词出现在全部 chunk；
- [ ] 查询词只出现在一个 chunk；
- [ ] 中文双字词；
- [ ] 英文大小写与连字符；
- [ ] 无命中；
- [ ] 损坏 metadata。

## 4. P1-8：知识库产品链路

当前同时存在服务端 Document/Chunk 和浏览器 localStorage 知识片段，两者的 UI 与开关没有形成一致模型。

计划：

- [ ] 确认 v0.1 以服务端 Document/Chunk 为唯一知识源；
- [ ] 接通上传、列表、删除和 RAG 开关；
- [ ] 展示命中文档、行号和分数；
- [ ] RAG capability 与全局开关语义保持一致；
- [ ] 删除未使用的旧状态和函数；
- [ ] 文档删除后不再被检索。

## 5. 评测基线

建立固定查询集，至少记录：

| 指标 | 说明 |
|---|---|
| Recall@5 | 目标 chunk 是否进入前 5 |
| MRR | 第一个相关结果的位置 |
| 无关结果率 | 返回结果中无关 chunk 比例 |
| 检索耗时 | 不同 chunk 数量下的耗时 |
| 引用正确率 | 展示来源是否与实际 chunk 一致 |

只有现有方案在真实样例上无法达到目标时，才进入向量检索 ADR。
