## 一、生成报告参考的资料从哪里来

### 1.1 证据链三层结构

```
用户上传文档 / GitHub 参考仓库
        ↓ 切块 (chunker.ts)
知识库 (DocumentChunk + 引用元数据)
        ↓ 检索 (TF-IDF / bge-m3 + RRF 混合)
报告中的 Evidence Finding (带 citation)
        ↓ 下游
implementation-manifest (路由/视觉/组件/验收标准)
```

**第一层：知识库输入**

| 来源类型 | 具体形式 | 代码位置 |
|---|---|---|
| 用户上传 | 产品需求文档、设计规范、技术方案 | `src/lib/rag/document-service.ts` |
| GitHub 参考 | UI 架构模式、设计系统代码片段 | `prisma/schema.prisma` (Document.sourceType) |
| 本地知识 | 项目文档、历史报告、评审记录 | `src/lib/capabilities/rag.ts` |

**第二层：检索与引用**

每个知识块 (Chunk) 都携带完整的引用元数据（`DocumentCitation` 类型）：
- `documentId` + `title` + `fileName` → 定位到具体文档
- `sourceType` + `sourceUrl` + `sourceVersion` → 来源类型与版本
- `license` + `reviewedAt` → 许可与审核时间
- `checksumSha256` → 防篡改校验
- `headingPath` + `startLine` + `endLine` → 精确到行号

**第三层：报告中的使用**

报告生成时，每个 Finding 必须绑定至少一个 EvidenceItem：
- `citationId` → 引用知识库中的 chunk
- `evidenceType` → 支持 / 反对 / 背景
- `sourceConfidence` → high / medium / low

### 1.2 当前状态（诚实标注）

| 组件 | 状态 | 说明 |
|---|---|---|
| 文档切块 (chunker) | **已实现** | 按标题路径 + 真实行号切块 |
| TF-IDF 检索 | **已实现** | 关键词匹配，确定性高 |
| 向量检索 (bge-m3) | **已实现** | 可选开关，需配置 embedding provider |
| 混合检索 (RRF) | **已实现** | TF-IDF + 向量融合排序 |
| 引用校验 | **已实现** | 生成报告时重新验证来源存在 |
| 知识库种子数据 | **待填充** | 需要用户上传或批量导入 GitHub 参考 |
| GitHub 自动爬取 | **未实现** | 设计为未来扩展 |

**核心问题**：知识库目前没有预置内容。报告质量取决于用户上传的文档质量。这是"证据链"的最大短板——**没有高质量输入，就没有高质量输出**。

## 二、如何测评结果是否合适

### 2.1 三级测评体系

```
┌──────────────────────────────────────────────────────┐
│  L1 机制验证（无需 API，已完成）                       │
│  - fault-recovery: 150/150 恢复率 100%               │
│  - Schema 校验、引用存在性检查                         │
│  - 211 Unit + 25 Core E2E 全过                        │
├──────────────────────────────────────────────────────┤
│  L2 消融实验（进行中，19/288 runs）                    │
│  - 4 组对比：单 Agent / 双候选无评审 / 单候选带评审 / 完整 │
│  - 24 案例 × 3 次重复 × 4 组 = 288 次运行            │
│  - 测量：覆盖率、约束满足率、输出一致性                  │
├──────────────────────────────────────────────────────┤
│  L3 人工盲评（待执行，需 20+ 案例 × 2 评分者）         │
│  - 盲评协议：baseline 直接提示 vs AgentForge 报告       │
│  - 5 维度评分：完整性、可行性、清晰度、创新性、总体       │
│  - 需要 2 个独立评分者 + 评分者间一致性检验              │
└──────────────────────────────────────────────────────┘
```

### 2.2 消融实验当前进度

| 指标 | 值 |
|---|---|
| 已完成 | 19 / 288 次运行 |
| 成功 | 17 次 (2 次 excluded，因结构化输出失败) |
| 已花费 | $0.91 USD |
| 预算上限 | $211.59 USD |
| 预计完成 | ~30-40 小时 |
| 当前 inFlight | lw-case-05-trial-1-single_candidate_with_review |

**四组实验臂**：
1. `single_agent` (5 completed) — 单 Agent 直接生成报告
2. `dual_candidate_no_review` (5 completed) — 双候选、无交叉评审
3. `single_candidate_with_review` (4 completed) — 单候选 + 带评审
4. `full_multi_agent` (5 completed) — 完整多 Agent 流程

### 2.3 盲评方案（待人工执行）

位于 `docs/quality - 质量评测/blind-evaluation-protocol.md`：

- 每个案例生成两个变体：baseline 直接提示 vs AgentForge 报告
- 评分者不知道哪个是哪个（盲评）
- 5 维度 × 5 分制 + 理由
- 需要 Krippendorff's α ≥ 0.67 的评分者间一致性

### 2.4 RAG 指标（待人工标注）

- Recall@5 / NDCG@10 / MRR
- 需要 100+ 人工标注查询
- 当前 golden set 状态：`not_ready`

## 三、项目有什么价值

### 3.1 核心交付物

**不是"分析报告"，而是"可执行的实施规格"**。

| 交付物 | 内容 | 用途 |
|---|---|---|
| Product/UI 报告 (3 套) | 产品定位、路由、视觉、组件、状态、流程、验收标准 | 指导开发或 AI 编程 |
| implementation-manifest (JSON) | 机器可读的实施规格，含 SHA-256 校验 | 下游 AI 编程工具直接消费 |
| 下游 Prompt | 面向 AI 编程工具的自然语言指令 | 复制到 Cursor / v0 / Bolt 生成网站 |

### 3.2 已验证的成果（来自仓库真实数据）

| 指标 | 结果 | 来源 |
|---|---|---|
| 完整质量门禁 | 211/211 Unit + 25/25 Core E2E | `npm run quality:all` |
| 代码覆盖率 (src/lib) | 91.55% 行 / 86.85% 分支 / 89.35% 函数 | CI 输出 |
| 报告回归测试 | 26/26 通过 | Core E2E |
| 故障恢复 | 150/150 场景恢复率 100% | fault-recovery 测试 |
| Demo 站点 | 3 个可运行页面 (attendance / atelier / nocturne) | `/generated/*` |

### 3.3 三个 Demo 站点的意义

这三个站点**不是 AgentForge 自动生成的**，而是**根据报告规格手工/AI 协作实现**的验证案例：

| 站点 | 形态 | 验证了什么 |
|---|---|---|
| Attendance OS | 企业级考勤工作台 | 数据密集 + 状态管理 + 操作流 |
| ATELIER | 数字艺术展览 | 视觉优先 + 沉浸式阅读 + 空间布局 |
| NOCTURNE | 数字聆听室 | 内容产品 + 发现/收藏/详情状态 |

**它们证明的是**：报告中的产品规格（路由、视觉、组件、状态、验收标准）足够指导下游实现不同形态的网站。

### 3.4 局限性（诚实标注）

| 局限 | 影响 | 未来方向 |
|---|---|---|
| 知识库无预置内容 | 报告质量取决于用户输入质量 | 批量导入 GitHub UI 参考 |
| 消融实验未完成 | 无法声称"多 Agent 比单 Agent 好 X%" | 等实验跑完（~30-40h） |
| 无人盲评 | 无法声称"报告质量优于 baseline" | 需 2 个评分者 × 20+ 案例 |
| 无真实用户验证 | 不确定报告是否真的能帮助开发 | 用户研究 / A/B 测试 |
| 未接入真实 AI 编程工具 | manifest → 网站的链路需人工中转 | API 集成 Cursor / v0 |

### 3.5 面试角度：项目能讲什么

按"功能层 / 设计层 / 工程层"三层回答：

**功能层（入场券）**：
- 多 Agent 协作将模糊需求转化为结构化实施报告
- 三套不同形态的 Demo 站点验证报告可指导实现

**设计层（及格线）**：
- 为什么选 LangGraph 而不是链式调用？→ 因为有分支、循环、人工等待
- 为什么用 TF-IDF 而不是直接向量检索？→ 小知识库确定性高，向量需 100+ 文档才有优势
- 为什么需要盲评而不是自动评分？→ 自动评分无法捕捉"可行性"和"创新性"

**工程层（加分项）**：
- 三级有效性模型区分"机制跑通"和"真实模型验证"
- tokenSource 溯源区分 provider 返回和本地估算
- 消融实验 + 盲评协议确保结论可验证
- Prisma + LangGraph Checkpoint 实现暂停/恢复/异常续跑

## 五、总结

**项目的核心创新不是"AI 生成报告"，而是"可验证的报告质量"**。

大多数多 Agent 项目只展示输出，不证明质量。AgentForge 的差异化在于：
1. 消融实验证明多 Agent 是否真的比单 Agent 好
2. 盲评协议证明报告是否真的比直接提示好
3. 证据链保证每个结论可追溯
4. 三级有效性声明避免"把机制跑通说成效果验证"

**当前最大的风险是**：如果消融实验最终显示多 Agent 和单 Agent 没有显著差异，项目的核心价值主张需要重新定位。
