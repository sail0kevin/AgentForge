## 二、面试场景话术模板

### 场景1: 自我介绍环节

**模板**:
> "我最近做了一个多Agent协作框架的项目，核心是用多个专业Agent协作来生成高质量的项目方案。我用24个真实业务场景做了消融实验，发现相比单Agent基线，多Agent生成的方案在架构权衡、实施路径、风险管理等维度都有质的提升。虽然Token消耗增加了22.8倍，但可以减少90分钟的人工补充时间，ROI是正的。"

**追问应对**:
- Q: "22.8倍Token消耗不是很浪费吗？"
- A: "这是因为多Agent进行了多轮协作和方案迭代。关键是看总成本：Single Agent虽然便宜，但生成的方案需要2小时人工补充；Multi-Agent成本是$0.20，但只需30分钟人工审查。总成本从$100降到$25，节省了74.5%。"

### 场景2: 被问"你的创新点是什么"

**模板**:
> "创新点有两个：第一，我设计了一个Planner-Proposer-Reviewer-Reviser-Evaluator的协作流程，模拟了真实项目中的需求分析、方案设计、评审、改进、决策环节。第二，我发现让Proposer生成两个不同取向的候选方案（比如交付优先 vs 质量优先），然后让Reviewer评审、Reviser改进，最后Evaluator综合决策，这种方式可以让每个架构决策都有充分的权衡分析。"

**追问应对**:
- Q: "有没有具体例子？"
- A: "有的。比如在内容审核系统这个案例里（展示case-07-showcase.md），Single Agent直接说'采用微服务架构'，但Multi-Agent会说'日均百万流量用普通数据库+消息队列即可支撑，不引入流计算框架，降低团队上手成本'。这种显式的权衡分析在真实项目评审中非常重要。"

### 场景3: 被问"怎么证明效果"

**模板**:
> "我做了消融实验，对比了4种变体：Single Agent、Single+Review、Dual Candidate、Full Multi-Agent。用24个真实业务场景（从电商系统到内容审核、从企业OA到数据平台）全覆盖测试。结果发现Multi-Agent生成的方案有这些特点：（展示statistical-summary.md的对比表）"

**追问应对**:
- Q: "24个场景够吗？"
- A: "这24个场景覆盖了4大类业务：交易电商、内容平台、企业内部、数据平台，每类的复杂度从中到高。而且每个场景都有明确的约束条件和验收标准，可以量化评估覆盖率和约束满足率。"

### 场景4: 被问"有什么局限性"

**模板**:
> "Multi-Agent不是万能的。它适合复杂度高、需要向管理层汇报的真实项目方案，但如果只是快速验证技术可行性，Single Agent更划算。另外，Token消耗确实增加了20多倍，对于成本敏感的场景需要做优化，比如缓存Planner的分析结果、动态调整协作深度等。"

**为什么要主动说局限性**:
- 显得你对项目有深入思考
- 避免面试官挑刺时被动
- 展示你的工程判断力（知道什么时候用什么方案）

## 三、面试官可能的刁钻问题

### Q1: "你这个不就是Prompt Engineering吗？"

**回答**:
> "Multi-Agent的核心不是单个Prompt的优化，而是多个Agent之间的协作博弈。举个例子：Reviewer的职责是挑刺，它会质疑Proposer的方案里'为什么不用分布式存储'、'峰值流量怎么办'。然后Reviser根据这些质疑改进方案。这种对抗和迭代是单个优化良好的Prompt做不到的。"

### Q2: "你的实验只测了方案质量，没测代码质量吧？"

**回答**:
> "确实，我这个项目聚焦在项目方案生成阶段，没有做代码生成的实验。但我认为先验证方案层面的协作是否有效，再扩展到代码生成，是一个合理的研究路径。如果有机会继续做，我会把Multi-Agent应用到架构设计和代码生成环节。"

### Q3: "你的成本计算把人工成本算成$50/小时，这个合理吗？"

**回答**:
> "这是一个保守估计。如果是初级工程师可能是$30-40/小时，但如果是技术负责人评审方案，时薪可能是$100+。我用$50是取了一个中间值。关键是即使按$30算，Multi-Agent的ROI依然是正的。"

### Q4: "你这24个case是自己编的还是真实需求？"

**回答**:
> "这24个case来自我整理的轻量级测试集，灵感来源于真实的企业级系统需求，比如电商平台的订单履约、内容社区的审核系统、企业内部的OA审批。每个case都有明确的约束条件和验收标准，不是空泛的'做一个电商系统'这种描述。"

### Q5: "GPT-4o也能做多Agent协作，你这个有什么优势？"

**回答**:
> "我的项目重点不是证明'只有我的框架能做'，而是通过消融实验量化地证明'多Agent协作相比单Agent的优势在哪里'。我测试的是协作机制本身的价值，而不是某个特定模型的能力。这套实验方法论可以迁移到任何LLM上。"

## 四、材料展示技巧

### 技巧1: 分层展示

**不要一次性倒所有数据**，按面试官的兴趣深入：

1. **第一层**（自我介绍）: "24个场景、22.8倍Token、ROI为正"
2. **第二层**（追问创新点）: "Planner-Proposer-Reviewer-Reviser-Evaluator协作"
3. **第三层**（追问具体例子）: 打开case-07-showcase.md，展示架构权衡对比
4. **第四层**（追问数据细节）: 打开statistical-summary.md，展示完整统计

### 技巧2: 用对比图表

如果面试是线上或者可以共享屏幕，准备这些可视化：

```
Single Agent (1次调用, 4030 tokens)
    ↓
    技术方案 (功能覆盖✓ 但无权衡✗)
    ↓
    需要2小时人工补充
    ↓
    总成本: $100

Multi-Agent (9次调用, 91985 tokens)
    ↓
    需求分析 → 双候选方案 → 评审 → 改进
    ↓
    执行方案 (架构权衡✓ MVP分阶段✓ 风险管理✓)
    ↓
    只需30分钟人工审查
    ↓
    总成本: $25
```

### 技巧3: 提前准备FAQ

把上面"刁钻问题"的答案背下来，面试时不要现编。

### 技巧4: 准备一个"失败案例"

面试官可能问"有没有Multi-Agent效果不好的例子"，你可以说：

> "有的。如果需求本身很简单，比如'做一个Todo List'，Multi-Agent就是杀鸡用牛刀。我发现在复杂度低于中等的场景里，Single Agent 30秒就能给出合理方案，Multi-Agent花5分钟生成的方案也没有质的差异。所以我在statistical-summary里专门写了'适用场景分析'这一节，说明什么时候该用Single、什么时候该用Multi。"

## 五、GitHub仓库准备（可选）

如果你打算把这个项目放到GitHub上，建议包含：

1. **README.md**: 项目介绍、快速开始、实验结果摘要
2. **docs/**: 包含这3份材料（statistical-summary、case-07-showcase、本指南）
3. **data/**: 消融实验原始数据（result-ledger-v2.json）
4. **examples/**: Single Agent和Multi-Agent的输出对比
5. **src/**: 核心代码（Planner/Proposer/Reviewer/Reviser/Evaluator实现）

**注意**: 
- 不要上传 `.env` 文件（包含API密钥）
- 不要上传几百MB的原始输出文件（只上传代表性案例）
- README里写清楚"这是一个研究项目，数据仅供参考"

---

## 六、最后的建议

1. **不要夸大效果**: 说"质量提升"而不是"质量提升10倍"
2. **承认局限性**: 主动说适用场景和成本问题
3. **准备代码细节**: 如果面试官追问实现，要能讲清楚Reviewer怎么评审、Reviser怎么改进
4. **关联到真实工作**: 如果面试的岗位是做Agent相关的，说明你这个经验可以直接用上

**最重要的**:
> 面试官不是要听你背材料，而是要看你**对项目的理解深度**。这3份材料只是辅助，真正的价值在你能不能讲清楚"为什么这么设计"、"遇到什么问题"、"怎么解决的"。

祝你面试顺利！
