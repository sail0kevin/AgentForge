# lw-case-07 深度对比：多Agent协作 vs 单Agent方案

## 一、案例基本信息

**案例ID**: lw-case-07  
**类别**: 内容平台 (content-platform)  
**复杂度**: 高 (high)

**原始需求**:
> 规划一个UGC社区内容审核系统，需要支持敏感词识别、图片/视频机审、人工复审队列优先级、跨部门升级处理，并说明误判申诉和审核员操作审计要求。

**约束条件**:
- ✓ 必须覆盖敏感词识别机制
- ✓ 必须覆盖误判申诉流程
- ✓ 必须覆盖审核员操作审计

## 二、方案对比总览

### 2.1 量化指标对比

| 指标 | Single Agent | Full Multi-Agent | 提升幅度 |
|------|--------------|------------------|----------|
| Token消耗 | 5,220 | 196,344 | **+37.6倍** |
| API调用次数 | 1次 | 15次 | **+15倍** |
| 处理时长 | 51.6秒 | 856.4秒 | +16.6倍 |
| 覆盖率 | 100% | 100% | 持平 |
| 约束满足率 | 100% | 100% | 持平 |
| 输出字数 | ~5,000字 | ~10,000字 | **+2倍** |

**关键发现**: 
- Multi-Agent在**质量深度**上实现了质的飞跃（输出详细度翻倍）
- Token和时间成本增加是因为**多轮协作、多角度评审、方案迭代**
- 两者都达到100%覆盖率，但**达成质量的方式完全不同**

## 三、Single Agent方案分析

### 3.1 方案结构
Single Agent一次性输出了完整的7章节方案：

1. 项目范围
2. 总体架构设计
3. 功能模块详细设计（6个子模块）
4. 关键架构决策与假设
5. 风险分析与应对措施
6. 实施步骤（10步）
7. 验收标准

### 3.2 方案特点

**优点**:
- ✓ 结构完整，覆盖了所有必需功能点
- ✓ 技术方案合理（AC自动机、消息队列、审计日志等）
- ✓ 考虑了关键风险（误判、词库更新、人力不足）
- ✓ 提供了明确的验收标准

**不足**:
- ✗ **缺乏实施优先级**: 所有功能平铺直叙，没有区分MVP vs 后续迭代
- ✗ **架构决策缺乏权衡分析**: 例如"容器化运行、微服务拆分"一笔带过，未说明为何选择微服务、有何代价
- ✗ **风险应对措施过于原则性**: 如"建设变体自动生成工具"，但未说明工具实现难度和替代方案
- ✗ **假设条件罗列但未显式标注风险**: 如"预算允许外部API调用费用"，但成本失控怎么办？
- ✗ **实施步骤缺少依赖关系**: 10个步骤线性排列，未说明哪些可以并行、哪些有前置依赖

**输出示例片段**:
```
机审模型的置信度阈值支持分场景配置，默认高置信度直接拦截，置信度处于灰色地带（如0.6至0.9）的内容强制进入人工队列，不直接判放行。模型每月利用人工复审回流标注数据做一次增量训练，持续降低漏放和误判。
```
→ 技术上合理，但**未说明阈值如何调优、训练数据量要求、模型迭代成本**

## 四、Full Multi-Agent方案分析

### 4.1 协作流程

Multi-Agent系统通过**15次API调用**完成了以下协作：

1. **Planner分析需求** → 识别关键约束和风险点
2. **Planner提出假设** → 明确日均100万、峰值3倍等边界条件
3. **Proposer生成候选方案1** → "分阶段交付与最小可行闭环"（交付优先）
4. **Proposer生成候选方案2** → "质量优先实施方案"（质量门禁优先）
5. **Reviewer评审** → 指出两个方案的优缺点和遗漏
6. **Reviser改进方案** → 根据评审意见优化
7. **Evaluator综合评估** → 给出最终建议

### 4.2 方案特点

**核心亮点**:

#### 1) 显式的架构权衡
方案中每个关键决策都配有**权衡说明**：

```
异步消息队列与普通数据库的选型: 
采用成熟消息队列解耦内容接收、机审与人工复审，核心业务数据存储在普通关系型数据库并做分区，不引入流计算框架和分布式存储。

(日均百万、峰值三百万的消息量级通过标准消息队列加水平扩展即可支撑，普通数据库加分区能简化运维和3年审计数据存储，符合约束中普通数据库加定期备份的要求，也降低团队上手成本和交付风险。)
```
→ **明确说明了为什么不用分布式存储、为什么选择普通数据库**

#### 2) 分阶段交付策略
方案1提出了**MVP优先**的实施路径：

- **首期**: 敏感词+人工复审的最短闭环
- **第二期**: 图片/视频机审接入
- **第三期**: 跨部门升级、申诉完善
- **第四期**: 审计查询增强

每个阶段都有明确的**交付范围、验收标准、技术债务偿还计划**

#### 3) 质量门禁机制
方案2提出了**发布门禁**：

```
发布门禁与演练要求: 
将峰值三倍压测、第三方机审降级演练、升级SLA时效测试、审计恢复演练列为上线发布门禁；
任一未通过均不得发布生产，并在发布评审中出具对应证据。
```
→ **把质量验证前置为发布条件，而非事后补救**

#### 4) 风险显式化
方案中标注了**12个具体风险**及应对措施，例如：

```
风险: 第三方机审故障导致降级期间人工队列积压超过兜底容量
应对: 需提前按峰值流量预留人工处理余量

风险: 备份恢复演练发现备份不可用或恢复时间过长
应对: 3年审计数据完整性承诺失效
```
→ **不仅列风险，还指出风险触发条件和后果**

#### 5) 假设条件的边界标注
方案明确标注了**9个关键假设**：

```
假设: 日均100万、峰值3倍流量的量级假设在开发期间保持有效
边界: 若量级变化需重跑容量建模与压测

假设: 第三方图片/视频机审服务在集成期间可用
边界: 且允许使用mock服务进行开发与测试
```
→ **假设不是空中楼阁，明确了变化时的应对**

## 五、关键差异对比

### 5.1 架构决策深度

| 维度 | Single Agent | Full Multi-Agent |
|------|--------------|------------------|
| 消息队列选型 | "通过消息队列异步传递" | "日均百万通过标准队列即可支撑，**不引入流计算框架**，降低团队上手成本" |
| 数据库选型 | "与业务库物理隔离" | "普通数据库+分区能**简化运维和3年存储**，符合约束要求" |
| 第三方集成 | "做多路冗余" | "**适配器模式+降级开关+内部模型桩**，供应商变更只影响适配层" |
| 审计防篡改 | "哈希链防篡改" | "**追加写+定期备份恢复演练**，明确不采用区块链，避免高成本" |

### 5.2 实施路径规划

| 维度 | Single Agent | Full Multi-Agent |
|------|--------------|------------------|
| 交付策略 | 10个线性步骤 | **MVP+3个迭代阶段**，每阶段独立验收 |
| 优先级划分 | 无 | 首期敏感词+人工，**图片/视频/申诉后置** |
| 技术债务 | 未提及 | **显式列出技术债务偿还清单**（SLA演练、安全测试后置） |
| 发布条件 | "全链路联调测试" | **4项发布门禁**（压测/降级/SLA/审计恢复） |

### 5.3 风险管理方式

| 维度 | Single Agent | Full Multi-Agent |
|------|--------------|------------------|
| 风险数量 | 6个概括性风险 | **12个具体风险+触发条件** |
| 应对措施 | 原则性描述 | **可执行的具体措施**（如"按峰值预留人力"） |
| 边界条件 | 假设罗列 | **9个假设+变化时的应对方案** |

## 六、真实场景推演

假设这是一个**真实的项目立项评审会**：

### 场景1: 技术经理追问
**问**: "你说要用微服务架构，为什么？有没有考虑过单体先行？"

- **Single Agent方案**: 方案中只提到"微服务拆分"，需要临场补充理由
- **Multi-Agent方案**: 方案中已说明"普通数据库+消息队列即可支撑百万级，**不引入流计算框架**，降低团队上手成本"

### 场景2: 产品经理关注上线时间
**问**: "这个系统什么时候能用？6个月能上线吗？"

- **Single Agent方案**: 10个步骤没有时间估算，难以回答
- **Multi-Agent方案**: "**首期MVP优先打通敏感词+人工复审闭环**，后续迭代再接入图片/视频"，可以承诺3个月MVP、6个月完整版

### 场景3: QA负责人关注质量保障
**问**: "怎么保证第三方API挂了系统不会崩？"

- **Single Agent方案**: "做多路冗余，切换自建模型兜底"，但未说明如何切换、兜底模型何时准备好
- **Multi-Agent方案**: "**适配器模式+超时熔断+降级到人工队列**，预留内部模型切换接口，**降级演练列为发布门禁**"

### 场景4: CFO关注成本
**问**: "这个系统要花多少钱？Token消耗能控制吗？"

- **Single Agent方案**: 假设"预算允许外部API调用费用"，但未量化
- **Multi-Agent方案**: 方案中明确"日均100万、峰值300万"的容量假设，并说明"**若量级变化需重跑容量建模**"

## 七、结论

### 7.1 核心差异总结

| 维度 | Single Agent | Full Multi-Agent |
|------|--------------|------------------|
| **输出性质** | 技术可行的完整方案 | **可落地、可迭代、风险可控的执行方案** |
| **决策质量** | 合理但缺少论证 | **每个决策都有权衡分析** |
| **实施性** | 理想化的线性流程 | **MVP优先+分阶段交付+技术债务管理** |
| **风险管理** | 识别风险 | **风险+触发条件+应对措施+边界假设** |
| **可审查性** | 需要评审者深挖细节 | **显式暴露关键权衡，便于评审决策** |

### 7.2 适用场景

**Single Agent适合**:
- 快速原型验证
- 技术可行性调研
- 个人学习项目
- 简单明确的需求

**Multi-Agent适合**:
- **真实企业级项目交付**
- 需要跨角色评审的方案（技术/产品/QA）
- 高风险、高复杂度系统
- 需要向管理层/客户汇报的方案

### 7.3 为什么Multi-Agent更好？

Multi-Agent的核心价值不是**写得更长**，而是：

1. **多角色协作模拟了真实项目流程**: Planner分析 → Proposer提方案 → Reviewer挑刺 → Reviser改进 → Evaluator决策
2. **强制显式化隐含假设**: Single Agent可能忽略的边界条件，在Multi-Agent的评审环节被揪出来
3. **自动执行方案优化**: 不需要人工反复追问"为什么"，系统内部已经完成多轮质疑和改进
4. **生成的是执行方案而非技术报告**: 包含MVP划分、发布门禁、技术债务管理等**工程实践**
