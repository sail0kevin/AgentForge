# AgentForge 答辩级工程报告写作规范
<!-- 文件名：reporting-standard - 答辩级报告写作规范 -->
<!-- 所属目录：remediation - 工程整改实施 -->

版本：1.0  
建立时间：2026-07-15  
适用范围：整改总报告、阶段报告、实验报告和最终答辩材料

## 1. 写作目标

本项目的工程报告以“博士论文级证据完整度、普通读者可理解的表达方式”为目标。这里的“论文级”指问题、方法、证据、实验、局限和结论完整，不意味着使用晦涩语言，也不意味着把简单问题故意写复杂。

每一章都必须回答五个白话问题：

1. 发生了什么？
2. 为什么这是问题？
3. 我们为什么选择这个方案？
4. 如何证明修改有效？
5. 还有什么没有解决？

## 2. 三层阅读结构

同一内容按三层组织，读者可以随时停止，而不会失去核心结论。

### 第一层：三分钟读懂

面向项目所有者、答辩老师和非技术读者，包括：

- 一句话结论；
- 修改前后的直观差异；
- 对用户的影响；
- 是否已经完成；
- 下一步是什么。

### 第二层：主报告

面向开发者和评审者，包括问题背景、方案比较、架构、数据结构、实施过程、测试结果、风险和局限。

### 第三层：技术附录

面向复现者，包括命令、环境、文件清单、Schema、事件样例、测试矩阵、失败实验、日志摘要和可追溯链接。

## 3. 总报告章节规范

最终报告至少包含以下章节：

1. 封面信息：项目、版本、时间、作者/执行者、报告状态；
2. 中文摘要：背景、问题、方法、结果和结论；
3. 关键词与术语表；
4. 项目背景与产品定位；
5. 研究问题与工程目标；
6. 整改前系统现状和基线；
7. 需求、约束与非目标；
8. 总体研究与实施方法；
9. 总体架构和数据流；
10. 各阶段方案、实现和证据；
11. 实验设计与测试环境；
12. 定量结果和定性分析；
13. 方案比较与技术决策；
14. 失败尝试、反例和修正过程；
15. 安全、隐私、成本与可维护性分析；
16. 有效性威胁和局限性；
17. 已完成贡献、遗留问题和后续路线；
18. 最终结论；
19. 参考资料；
20. 附录：命令、文件、事件、Schema 和完整验证矩阵。

## 4. 阶段报告强制结构

每个 Phase 报告至少包含：

- 阶段摘要：用白话说明本阶段做了什么；
- 背景与问题定义；
- 修改前证据；
- 目标、非目标和约束；
- 研究问题或验收问题；
- 候选方案及比较；
- 最终设计与选择理由；
- 数据模型、状态机或流程图；
- 分步骤实施记录；
- 文件级修改清单；
- 实验设计、环境和测试数据；
- 成功结果和失败尝试；
- 修改前后对比；
- 安全、兼容性和性能影响；
- 局限、遗留风险和下一阶段依赖；
- 可复现命令和证据索引。

## 5. 单个问题记录模板

```text
问题 ID / 标题 / 优先级 / 状态
→ 普通人解释
→ 技术定义
→ 发现方式与证据
→ 影响范围和失败场景
→ 根因
→ 候选方案 A/B/C
→ 选择及理由
→ 修改文件与关键逻辑
→ 测试方法和结果
→ 失败实验与修正
→ 剩余风险
→ 完成判定
```

## 6. 证据等级

| 等级 | 证据 | 可以支持的表述 |
|---|---|---|
| E0 | 推测或待验证 | 只能写“可能”“待确认” |
| E1 | 静态代码检查 | 可以说明代码结构和明显分支 |
| E2 | 单元测试或定向复现 | 可以说明局部规则有效 |
| E3 | 隔离数据库集成/E2E | 可以说明真实链路行为 |
| E4 | 生产构建、性能或多环境验证 | 可以说明交付和环境适应性 |
| E5 | 长期运行或真实用户数据 | 才能支持生产稳定性结论 |

报告不能用 E1 证据宣称生产稳定，也不能因为构建通过就宣称业务正确。

## 7. 实验记录规范

每个实验记录：

- 实验编号和目的；
- 前置条件、环境、数据和变量；
- 操作步骤与命令；
- 预期结果；
- 实际结果；
- 是否通过；
- 异常、解释和复测结果；
- 对结论的支持范围。

失败实验不得删除。例如并发测试第一次失败时，应记录“为什么失败、暴露了什么真实行为、如何修改测试或实现”。

## 8. 可读性规则

1. 每章先写白话摘要，再写技术细节。
2. 一个句子尽量只表达一个主要观点。
3. 专业术语第一次出现时，紧跟一句普通话解释。
4. 代码只展示帮助理解的最小片段，完整内容链接到文件。
5. 三个以上状态或步骤优先使用表格、流程图或时序图。
6. 不使用“显然、简单、众所周知”等要求读者自行理解的表达。
7. 数字必须说明来源、时间、环境和统计口径。
8. 结论必须区分“已证明、合理推断、尚未验证”。

## 9. 图表与示例规则

- 架构图解释组件关系；
- 时序图解释请求、锁、Agent、数据库和 SSE 的先后顺序；
- 状态图解释运行状态变化；
- 对比表解释方案选择；
- 测试矩阵解释覆盖范围；
- 具体用户场景解释技术问题对普通人的影响。

图表之后必须有文字解读，不能要求读者只看图自行推断。

## 10. 更新与审查

每完成一个修改单元：

1. 更新阶段报告的实施记录和实验结果；
2. 更新整改总览的状态和数字；
3. 更新 `current-status - 当前开发状态.md` 的已实现事实；
4. 更新 `project-memory - 项目长期记忆.md` 的长期决策；
5. 检查报告结论是否超过现有证据；
6. 检查相对链接、日期、术语和状态是否一致。

最终答辩前再生成摘要版、完整正文和技术附录；三者共享同一证据来源，避免出现三个互相冲突的版本。
