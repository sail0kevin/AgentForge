## 日常阅读精简

不需要逐份阅读全部 36 份文档。日常开发或交接时，只需先看以下五份：

1. `README - 文档索引.md`：从这里进入对应主题；
2. `ai-handover-2026-07-16 - AI接手交接说明.md`：给新接手人员或 AI 的项目全貌；
3. `current-status - 当前开发状态.md`：当前已经实现什么、还缺什么；
4. `project-memory - 项目长期记忆.md`：不能随意改变的长期决策与优先级；
5. `demo - 本地演示指南.md`：如何实际启动和演示。

`design/` 和 `remediation/` 是需要深入设计、整改或答辩时才查阅的工程证据；`reviews/` 与 `archive/` 只保存历史评审和旧版本材料，不参与日常判断。

Phase 7的前端拆分、Workspace-Agent原子绑定和Web/Electron交付边界详见[质量与交付报告](remediation - 工程整改实施/phase-7-quality-and-release - 质量与交付边界.md)。

## 当前目录职责

| 位置 | 职责 | 状态要求 |
|---|---|---|
| `current-status - 当前开发状态.md` | 当前事实唯一入口 | 每次阶段交付后更新日期和验证证据 |
| `architecture - 当前运行架构.md` | 当前已经运行的架构 | 不写尚未接入主链路的能力 |
| `demo - 本地演示指南.md` | 可复现演示 | 命令、模型和页面必须真实可用 |
| `design/` | 未来目标设计 | 必须明确标注“目标设计”或“原型” |
| `reviews/` | 带日期的阶段评审 | 保留当时工作区、证据和结论，不覆盖历史 |
| `remediation/` | 评审问题的整改执行记录和完整主报告 | 总览管进度，阶段报告保留过程，主报告汇总当前完整结论 |
| `reports/` | 对外项目报告和发布清单 | 只陈述有代码和验证证据支持的能力 |
| `archive/` | 被新版本取代的报告和旧整改路线 | 不作为当前依据，保留来源、日期和替代文档 |
| `screenshots/` | 审查后的公开截图 | 不包含密钥、个人信息和本机路径 |
| `project-memory - 项目长期记忆.md` | 稳定项目记忆 | 只保存长期有效事实、决策和当前优先级 |

## 是否需要进一步拆分

当前共有 36 份 Markdown，阅读入口确实偏多；但其中包含阶段证据、评审和归档，不能简单按数量删除。当前通过“根目录必读、工程证据、历史归档”三层导航降低阅读负担；不建议立即移动 `architecture - 当前运行架构.md`、`current-status - 当前开发状态.md` 和 `demo - 本地演示指南.md`，否则会产生不必要的链接改动。`quality/` 已因盲评协议与后续实验结果形成独立主题；其他主题在出现至少两到三份文档时，再按需增加：

- `decisions/`：架构决策记录，例如是否全面迁移 LangGraph、是否升级向量检索、Web 与 Electron 的产品选择。
- `operations/`：安装、数据库迁移、密钥轮换、备份恢复、故障排查和桌面打包。
- `quality - 质量评测/`：已创建；存放[盲评协议](quality - 质量评测/blind-evaluation-protocol - 真实模型盲评协议.md)和未来已解盲的质量结果，不保存原始报告或私有解盲表。
- `contracts/`：SSE 事件、Run 状态机、错误码和 Tool Schema；仅在契约内容增长后创建。

不要提前创建大量空目录。新增文档时先判断它属于“当前事实、正式设计、阶段评审、整改执行、公开报告、历史归档、长期记忆”中的哪一类。

## 文档维护规则

1. `current-status - 当前开发状态.md` 是当前实现状态的唯一事实源；其他文档引用它，不重复维护相互冲突的状态。
2. 每项“已实现”能力至少关联一个验证命令、测试或可复现步骤。
3. 带日期的评审文档只追加新的评审，不回写历史结论；路线发生变化时创建新复查，并将明确被取代的报告移入 `archive/`。
4. 目标设计进入代码主链路后，先更新当前架构和测试证据，再修改公开报告。
5. 发布前检查所有相对链接，并确认 `.env`、数据库、测试产物和本地材料没有进入提交。
6. `remediation/final-report - 工程整改与开发总报告.md` 始终保持“当前内容完整”：未实现项写明证据缺口和验收条件，不保留空白占位。
